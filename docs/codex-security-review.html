Executive Summary

Overall posture

The application has a strong security baseline in several areas: authenticated API routes are generally tenant-scoped, raw SQL is parameterized, RLS is present, source maps and framework branding are disabled, and the unit/typecheck suite passes. The highest residual risk is concentrated in privileged operational paths, upload/storage handling, recoverable authentication tokens, SSRF via Web Push, and vulnerable production dependencies.

Immediate priorities

  1. Fail closed for all cron endpoints when CRON_SECRET is absent.
  2. Harden file uploads with magic-byte validation, forced safe extensions, and private storage for signatures.
  3. Hash verification identifiers and encrypt OAuth provider tokens in Better Auth.
  4. Validate Web Push endpoints against private IP and metadata targets.
  5. Patch vulnerable production packages and add CI gates for audit regressions.

Test Methodology

The audit used a multi-agent swarm model covering OWASP Top 10 plus extended checks for modern Next.js, API business logic, client-side state, CI/CD integrity, and observability. Each sub-agent performed static analysis and targeted local command verification. The orchestrator reconciled agent outputs, removed duplicate or unsupported claims, and retained findings backed by file, line, command, or package-lock evidence.

Detailed Findings

F-01 Cron endpoints fail open when CRON_SECRET is missing

HighAgent 01OWASP A01 Broken Access ControlAgent 05

Location

app/api/cron/keep-alive/route.ts:21-28, app/api/cron/notifications/route.ts:70-77, app/api/cron/trial-lifecycle/route.ts:25-30, lib/env.ts:188-190.

Explanation

Each cron route only verifies the bearer token when env.CRON_SECRET is set. Because the variable is optional and absent from the template, a production deployment without it exposes privileged cron work to unauthenticated callers.

Proof of Concept / Failure Context

A request without authorization would pass the guard whenever CRON_SECRET is unset. These handlers call privileged paths such as adminQuery(), push notifications, and lifecycle email writes.

Remediation

Require CRON_SECRET in production startup validation, fail closed if absent, use constant-time comparison, and add deployment checks for Vercel cron headers or an equivalent trusted scheduler identity.

F-02 Upload MIME and extension bypass enables same-origin active content

HighAgent 03OWASP A03 InjectionAgent 13

Location

app/api/profile/logo/route.ts:18-19, app/api/profile/signature/route.ts:18-19, lib/storage.ts:65-82.

Explanation

The upload routes trust file.type and the storage layer preserves the client-supplied filename extension. In local or fallback storage, files are written under public/uploads, making them same-origin web content.

Proof of Concept / Failure Context

A multipart upload with filename="poc.html", Content-Type: image/png, and HTML/script bytes can be stored as /uploads/logos/<user>_<timestamp>.html. If visited, the browser treats it as same-origin active content.

Remediation

Validate magic bytes, allow only safe extensions derived from the verified MIME type, transcode uploads to PNG/WebP, set X-Content-Type-Options: nosniff, and serve user uploads from private or cookieless storage.

F-03 Public uploaded signatures and logos expose sensitive assets

HighAgent 01OWASP A01 Broken Access ControlAgent 02

Location

lib/storage.ts:65-68, lib/storage.ts:116-120, app/api/profile/signature/route.ts:81-82, app/api/profile/logo/route.ts:81-82.

Explanation

Generated object keys include the user id and timestamp, and cloud uploads use public access. A handwritten signature image is sensitive and should not be exposed through a permanent public URL.

Proof of Concept / Failure Context

Any party with a stored signature URL can retrieve it without authentication. Key structure also leaks internal user identifiers and approximate upload time.

Remediation

Store signatures in private object storage with random UUID keys. Return short-lived signed URLs or serve through an authenticated proxy that verifies current_user.id before streaming the file.

F-04 Password reset tokens stored as recoverable identifiers

HighAgent 02OWASP A02 Cryptographic FailuresAgent 07

Location

src/db/schema.ts:76-82, lib/auth/better-auth.ts:243-335, dependency behavior in node_modules/better-auth/dist/db/verification-token-storage.mjs and node_modules/better-auth/dist/api/routes/password.mjs.

Explanation

The verification table stores text identifiers and values. Better Auth defaults to storing verification identifiers in plain form unless verification.storeIdentifier is configured. Reset tokens are embedded in identifiers such as reset-password:<token>.

Proof of Concept / Failure Context

A database read of the verification table can expose live password reset tokens before expiration, turning a DB read into account takeover capability.

Remediation

Configure Better Auth with verification: { storeIdentifier: "hashed" } or an HMAC-backed hasher. Expire existing verification rows after deployment and monitor for unexpected verification reads.

F-05 Password reset and verification URLs can be logged

HighAgent 02OWASP A09 Logging FailuresAgent 07

Location

lib/auth/better-auth.ts:277-280, lib/auth/better-auth.ts:303-305, lib/email.ts:48-52, lib/logger.ts:160-162.

Explanation

When email delivery is not configured or fails, the auth configuration logs full reset and verification URLs. The production logger defaults to INFO, so bearer-style account recovery links can enter centralized logs.

Proof of Concept / Failure Context

Disable or omit RESEND_API_KEY, request a reset, and inspect logs. The reset URL includes a live token capable of taking over the account before it expires.

Remediation

Never log full recovery links outside local development. Require email configuration in production, log only event metadata and redacted token hashes, and add automated log redaction for query parameters named token.

F-06 OAuth provider tokens stored plaintext by default

HighAgent 02OWASP A02 Cryptographic FailuresAgent 07

Location

src/db/schema.ts:63-65, lib/auth/better-auth.ts:308-314, dependency behavior in node_modules/better-auth/dist/oauth2/utils.mjs:12-23.

Explanation

The account table includes access_token, refresh_token, and id_token columns. Better Auth only encrypts OAuth tokens when account.encryptOAuthTokens is enabled, and the local config does not set it.

Proof of Concept / Failure Context

A database compromise or overly broad admin read can expose provider refresh tokens and Google identity tokens in recoverable form.

Remediation

Enable account: { encryptOAuthTokens: true }, rotate or revoke existing provider credentials, and restrict DB roles that can read token-bearing columns.

F-07 Web Push endpoint blind SSRF

HighAgent 10OWASP A10 SSRFAgent 12

Location

app/api/push/subscribe/route.ts:34-55, lib/push.ts:73-79, app/api/cron/notifications/route.ts:102-150.

Explanation

The subscription route stores arbitrary push endpoints, and the notification worker later sends server-side HTTPS requests to those endpoints. There is no allowlist or private-network rejection.

Proof of Concept / Failure Context

An authenticated user can register an endpoint such as https://127.0.0.1:8443/push or another internal HTTPS service. The cron notification job then performs a blind server-side POST.

Remediation

Require HTTPS, reject IP literals and private/link-local/metadata ranges after DNS resolution, consider allowlisting known push provider hosts, enforce request timeouts, and prune invalid endpoints aggressively.

F-08 taskId is not proven to belong to the current user/project

HighAgent 01OWASP A01 Broken Access ControlAgent 12

Location

app/api/timer/start/route.ts:43-60, app/api/entries/route.ts:152-200, app/api/entries/[id]/route.ts:94-148, lib/transformers/entries.ts:40-44, src/db/schema.ts:384-386.

Explanation

The routes validate the project owner but do not prove that the provided taskId belongs to that same user and project before inserting or updating entries. The schema foreign key only checks that the task id exists.

Proof of Concept / Failure Context

If Alice knows Bob's task id, she can submit her own projectId with Bob's taskId. Later joins can leak the task title or create cross-user referential contamination.

Remediation

Inside the same transaction, validate tasks.id = taskId AND tasks.user_id = current_user.id AND tasks.project_id = projectId. Add a composite FK or trigger to enforce task-project-user consistency at the database layer.

F-09 Charge document issuance can double-bill under concurrency

HighAgent 04OWASP A04 Insecure DesignAgent 12

Location

app/api/charge-documents/route.ts:90-104, app/api/charge-documents/route.ts:157-193, src/db/schema.ts:553-564.

Explanation

The handler selects entries where charge_document_id IS NULL, inserts document lines, and only later updates entries. There is no row lock, atomic claim, affected-row verification, or unique line constraint on time_entry_id.

Proof of Concept / Failure Context

Two concurrent requests with the same timeEntryIds can both insert charge document lines. One update may claim the entries, while the other document still contains billable lines.

Remediation

Atomically claim entries before inserting lines using SELECT ... FOR UPDATE or a guarded UPDATE ... RETURNING. Verify row counts and add a partial unique index preventing more than one active charge line per time entry.

F-10 Admin cross-user delete can partially execute under RLS

HighAgent 01OWASP A01 Broken Access ControlAgent 09

Location

app/api/admin/users/[id]/actions/route.ts:41-43, app/api/admin/users/[id]/actions/route.ts:101-112, drizzle/rls-policies.sql:32-39.

Explanation

The admin delete flow uses tenant-scoped query() for cross-user data while RLS filters rows by the current admin's user id. This can delete auth rows that are not covered by the same RLS assumptions while leaving app rows behind.

Proof of Concept / Failure Context

An admin deleting another user may execute statements that affect only non-RLS or differently scoped tables. The operation can appear successful while orphaning or retaining user-owned business data.

Remediation

Use a dedicated privileged admin transaction helper for cross-tenant writes, verify each affected row count, cover all owned tables, and emit an audit event with actor, target, reason, and request id.

F-11 Missing durable audit trail for admin and financial mutations

HighAgent 09OWASP A09 Logging and Monitoring FailuresAgent 04

Location

app/api/admin/users/[id]/actions/route.ts:78-112, app/api/charge-documents/[id]/pay/route.ts:13-17, app/api/charge-documents/[id]/cancel/route.ts:16-30, src/db/schema.ts.

Explanation

High-impact events such as admin suspension/deletion, marking documents paid, canceling documents, and re-opening financial records do not write to a durable immutable audit table.

Proof of Concept / Failure Context

The schema contains business tables but no central audit_events table. Console logs alone cannot answer who performed a sensitive mutation, from which session, or with what before/after state.

Remediation

Add an append-only audit_events table and write audit rows in the same transaction as each sensitive mutation. Include actor id, action, resource type/id, before/after hashes, IP, user agent, and request id.
