Executive Summary

A comprehensive security audit was conducted on the ClockBill time-tracking and billing application using 13 specialized sub-agents, each targeting a distinct OWASP category or security domain. The audit covered all 59 API routes, authentication system, database layer, client-side code, CI/CD pipeline, and dependency tree.

Overall Risk Assessment: MEDIUM. The application demonstrates strong foundational security — all SQL queries are parameterized, all API routes enforce authentication and ownership checks, RLS provides defense-in-depth tenant isolation, and input validation is consistently applied via Zod schemas. No critical-severity vulnerabilities were found. However, several high-severity gaps exist, primarily around missing security headers, absent rate limiting on business endpoints, and insufficient security logging/audit trails.

High-Severity Findings

High

H-01: Missing HTTP Security Headers

OWASP: A05 — Security Misconfiguration
Location: next.config.mjs — no headers() function defined
Description:

The application sends zero HTTP security headers. Missing: Content-Security-Policy, Strict-Transport-Security (HSTS), X-Frame-Options, X-Content-Type-Options, Referrer-Policy, and Permissions-Policy.

Impact:

Without HSTS, MITM attackers can downgrade HTTPS to HTTP. Without CSP, XSS payloads can exfiltrate data to attacker domains. Without X-Frame-Options, clickjacking is possible. Without X-Content-Type-Options, MIME sniffing attacks are possible.

Remediation: 
// next.config.mjs — add headers()
async headers() {
  return [{
    source: "/(.*)",
    headers: [
      { key: "X-Frame-Options", value: "DENY" },
      { key: "X-Content-Type-Options", value: "nosniff" },
      { key: "Referrer-Policy", value: "strict-origin-when-cross-origin" },
      { key: "Permissions-Policy", value: "camera=(), microphone=(), geolocation=()" },
      { key: "Strict-Transport-Security", value: "max-age=63072000; includeSubDomains; preload" },
      { key: "Content-Security-Policy", value: "default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https:; font-src 'self' data:; connect-src 'self' https://*.sentry.io wss:; frame-ancestors 'none';" },
    ]
  }];
}
High

H-02: Timer Stop Accepts Client-Supplied Arbitrary Duration

OWASP: A04 — Insecure Design
Location: app/api/timer/stop/route.ts:65-66
Description:

The stop endpoint accepts an optional duration field from the client body. When present, it is used directly as the entry's duration in minutes, completely bypassing the server-side calculation from start_time → end_time.

Exploit:

A user starts a timer, waits 1 minute, stops it with { duration: 999999 }. The entry is stored with 999999 minutes (~694 days) of billable time. If the entry is later included in a charge document, the client is billed for fabricated hours.

Remediation:

Remove the custom duration override entirely, or cap it at actual_elapsed_time * 1.1. The server should always compute duration from end_time - start_time - paused_time.

High

H-03: Manual Time Entry Has No Duration Cap

OWASP: A04 — Insecure Design
Location: lib/schemas/entries.ts:17
Description:

The entry body schema validates duration: z.number().min(0) with no upper bound. Users can create manual entries with millions of minutes of duration. Combined with H-02, there is no server-side ceiling on billed time per entry.

Exploit:

POST /api/entries with { duration: 999999999, rate: 500 } creates an entry worth ~83 billion ILS.

Remediation:

Add .max(1440) (24 hours) to the duration field in the Zod schema. Apply the same cap to quantity for item billing.

High

H-04: No Rate Limiting on Authenticated API Write Endpoints

OWASP: A04 — Insecure Design / A12 — API Security
Location: All app/api/ routes (30+ write endpoints)
Description:

Better Auth provides database-backed rate limiting for auth endpoints (sign-in: 5/min, sign-up: 5/min). However, all 30+ authenticated write endpoints have zero rate limiting. A compromised session or malicious authenticated user can call them as fast as the server allows.

Exploit:

Script calls POST /api/timer/start in a tight loop creating thousands of running timers. Or repeatedly calls POST /api/charge-documents to flood the doc_number counter.

Remediation:

Implement a per-user rate limiter middleware (e.g. Upstash Ratelimit or Next.js middleware with token-bucket). Priority: write endpoints first, especially bulk operations and charge document creation.

High

H-05: Sentry Tunnel Route Open Abuse Surface

OWASP: A05 — Security Misconfiguration
Location: next.config.mjs:32, proxy.ts:36,189
Description:

The tunnelRoute: "/monitoring" creates an unauthenticated server-side proxy to Sentry's ingest endpoint. No rate limiting. An attacker can flood it to exhaust Sentry event quota or pollute error data with false positives.

Remediation:

Add rate limiting at the Vercel Edge/CDN level for /monitoring. Consider Vercel WAF rules to restrict the endpoint.

High

H-06: No Authentication Event Logging

OWASP: A09 — Security Logging Failures
Location: app/api/auth/[...all]/route.ts, app/api/auth/logout/route.ts
Description:

The Better Auth catch-all handler delegates all auth endpoints with zero logging — no successful logins, no failed logins, no sign-ups, no logouts. An attacker brute-forcing credentials leaves no log trail.

Remediation:

Add Better Auth databaseHooks or event middleware to log sign-in success/failure, sign-up, and sign-out with timestamp, userId, IP, and method.

High

H-07: No Authorization Failure Logging on Admin Endpoints

OWASP: A09 — Security Logging Failures
Location: All 5 app/api/admin/ routes
Description:

All admin routes check getAdminUser() and silently return 403 when it fails. No log entry is created for failed authorization attempts. An attacker probing admin endpoints goes completely undetected.

Remediation:

Log every failed admin access attempt with userId, IP, and requested path.

High

H-08: No Audit Trail for Destructive Admin Actions

OWASP: A09 — Security Logging Failures
Location: app/api/admin/users/[id]/actions/route.ts:60-114
Description:

Admin actions — verify_email, delete_sessions, toggle_role, delete_user — execute without any logging. An admin can delete an entire user account with no audit record.

Remediation:

Log every admin action with admin userId, target userId, action performed, timestamp, and IP. Consider persisting to a dedicated admin_audit_log table.

High

H-09: Reports Endpoint — Unbounded Result Set, No Pagination

OWASP: A12 — API & Business Logic
Location: app/api/reports/route.ts:95, app/api/reports/excel/route.ts:186
Description:

Both the JSON report and Excel export endpoints execute with no LIMIT clause. A user with years of data will have the entire dataset fetched, aggregated in-memory (multiple reduce() passes), and serialized. Repeated requests cause memory pressure.

Remediation:

Enforce mandatory startDate/endDate parameters, or add a hard LIMIT (e.g. 50,000 entries). Add a max-row cap for Excel export.

Medium-Severity Findings

Medium

M-01: CRON_SECRET Protection is Fail-Open

OWASP: A01 — Broken Access Control / A04 — Insecure Design
Location: app/api/cron/keep-alive/route.ts:22-28, app/api/cron/notifications/route.ts:71-77, app/api/cron/trial-lifecycle/route.ts:26-29
Description:

All three cron endpoints guard access with if (secret) — when CRON_SECRET is not set, the entire auth check is skipped and the endpoint is publicly accessible. The trial-lifecycle cron uses adminQuery (bypasses RLS) and processes all users.

Remediation:

Fail closed when CRON_SECRET is absent. Add startup validation in lib/env.ts that makes CRON_SECRET required when NODE_ENV=production.

Medium

M-02: Password Reset Token Logged in Dev Mode

OWASP: A02 — Cryptographic Failures / A09 — Logging
Location: lib/auth/better-auth.ts:279, :304
Description:

When RESEND_API_KEY is not configured, the full password reset URL (containing the one-time token) is logged via logger.info(). If a production deployment has a broken Resend key, these tokens appear in production logs.

Remediation:

Gate these log statements on NODE_ENV !== 'production', or redact the token from the URL.

Medium

M-03: No Server-Side Password Complexity Enforcement

OWASP: A07 — Auth Failures
Location: lib/auth/better-auth.ts:260
Description:

Server-side password policy only enforces minPasswordLength: 8. The PasswordStrengthIndicator is client-side only — an attacker can bypass it via direct API calls with a weak password like aaaaaaaa.

Remediation:

Add server-side password.validate callback in Better Auth config requiring uppercase, lowercase, digit, and special character.

Medium

M-04: No Explicit Session Expiration Configuration

OWASP: A07 — Auth Failures
Location: lib/auth/better-auth.ts:316-319
Description:

No explicit expiresIn or updateAge is set. Better Auth defaults to 7-day session lifetime with no sliding expiration. A stolen session token remains valid for up to 7 days.

Remediation: 
session: {
  cookieCache: { enabled: true, maxAge: 300 },
  expiresIn: 86400,    // 24 hours
  updateAge: 3600,     // Refresh every 1 hour
}
Medium

M-05: No Account Lockout After Repeated Failures

OWASP: A07 — Auth Failures
Location: lib/auth/better-auth.ts:325-336
Description:

Rate limiting exists (5 attempts/60s), but there is no persistent account lockout. After the 60-second window resets, the attacker gets another 5 attempts. Low-and-slow brute force: ~7,200 guesses/day per account.

Remediation:

Add exponential backoff or persistent lockout after N cumulative failures (e.g. 20 failures in 24 hours).

Medium

M-06: Docker PostgreSQL Exposed on Host with Default Credentials

OWASP: A05 — Security Misconfiguration
Location: docker-compose.yml:8-12
Description:

The PostgreSQL container binds to 0.0.0.0:5432 (all interfaces). Default credentials clockbill:clockbill_dev are used when env vars are not set. Any device on the same network can connect.

Remediation:

Bind to localhost only: "127.0.0.1:5432:5432"

Medium

M-07: In-Memory Contact Rate Limit Is Ephemeral and IP-Spoofable

OWASP: A04 — Insecure Design
Location: app/api/contact/route.ts:14-25
Description:

Rate limit stores hits in a module-level Map. Resets on every cold start. x-forwarded-for is trivially spoofable. Memory grows unboundedly.

Remediation:

Use a persistent rate limit store. Add Cloudflare-level rate limiting on /api/contact.

Medium

M-08: Charge Document computedLines Amounts Trusted from Client

OWASP: A12 — API & Business Logic
Location: app/api/charge-documents/route.ts:117-131
Description:

When creating a charge document, computedLines (fixed monthly charges) have their amount field sent by the client and stored directly. The server never recalculates or validates these amounts against the project's fixed_monthly_fee.

Remediation:

Server-side, recompute fixed monthly charges from DB-stored project data and compare against client-supplied amounts. Reject mismatches.

M-09: List Endpoints Lack Pagination

OWASP: A12 — API & Business Logic

Clients, projects, tasks, and charge-documents list endpoints return ALL rows with no LIMIT clause. Power users with large datasets generate large payloads.

Medium

M-10: Logger Has No Sanitization for Sensitive Data

OWASP: A09 — Logging Failures
Location: lib/logger.ts:118-125
Description:

The formatMessage method serializes all metadata via JSON.stringify(meta) with no filtering. Any caller that passes a password, token, or authorization field will have it written to stdout and forwarded to Sentry.

Remediation:

Add a sanitization function that redacts keys matching /password|token|secret|authorization|cookie|api.?key/i.

Medium

M-11: Inconsistent Logging — 46 console.error Calls Bypass Logger

OWASP: A09 / A05
Location: 30+ API route files across app/api/
Description:

46 console.error() calls across API routes bypass the structured logger — no Sentry reporting, no structured metadata, no consistent format. All 5 admin routes use console.error instead of logger.error.

Remediation:

Migrate all API route error handlers from console.error to logger.error().

Medium

M-12: No IP Address Logging on Security Events

OWASP: A09 — Logging Failures
Location: All auth and admin routes
Description:

The application never captures client IP addresses for security-relevant events. Auth events, admin actions, and authorization failures have no IP context. Incident response cannot determine attack origin.

Remediation:

Log x-forwarded-for alongside all security events.

Medium

M-13: Admin Pages Lack Server-Side Auth Guard

OWASP: A11 — Framework Risks
Location: app/[locale]/admin/page.tsx, app/[locale]/admin/users/page.tsx, app/[locale]/admin/stats/page.tsx
Description:

All admin pages are "use client" components. The admin role check happens client-side. The full admin page bundle (HTML + JS) is sent to non-admin users before the client-side redirect fires.

Remediation:

Add a server component layout at app/[locale]/admin/layout.tsx that checks getUser() + role === "admin" and calls redirect() for non-admins.

The health endpoint returns "database": "connected" or "database": "disconnected" to unauthenticated callers, revealing infrastructure state to attackers.

M-16: SELECT * in Charge Document Endpoint

Passed Security Tests

The following checks were verified and passed, demonstrating the application's strong security foundations:

A01 — Access Control

  • All 59 API routes call getUser() and return 401 if unauthenticated
  • Every resource query filters by WHERE user_id = $2 — no IDOR gaps
  • Bulk operations scoped with WHERE id IN (...) AND user_id = $N
  • Admin endpoints protected by getAdminUser() role check
  • RLS defense-in-depth: app.current_user_id set via set_config() per query
  • SAFE_USER_ID regex prevents SQL injection through tenant context
  • CORS defaults to same-origin (no explicit CORS headers)
  • Role escalation prevented: input: false on role field
  • Admin self-protection: cannot delete/toggle own role
  • Plan-lock enforcement via getLockedClientIds()

A02 — Cryptographic

  • No .env files tracked in git
  • .gitignore covers all .env* patterns
  • No hardcoded secrets in source code
  • BETTER_AUTH_SECRET validated ≥32 chars at startup
  • Password hashing managed by Better Auth (bcrypt/scrypt)
  • Sentry sendDefaultPii: false in all configs
  • NEXT_PUBLIC_ vars contain only public-safe values
  • VAPID private key stays server-side only
  • Webhook signature verification on Polar webhooks
  • Email verification enforced when Resend is configured

A03 — Injection

  • All 50+ SQL queries use parameterized placeholders ($1, $2)
  • Dynamic SQL construction uses parameterized placeholders, not value interpolation
  • All write endpoints validated with Zod schemas via parseBody()
  • All user text fields have max length constraints (100–5000 chars)
  • React auto-escapes all user data rendered in JSX
  • dangerouslySetInnerHTML only used with hardcoded script (no user input)
  • Email HTML output escaped with escapeHtml()
  • No eval(), new Function(), or child_process.exec()

A04 — Design

  • Auth rate limiting: sign-in 5/min, sign-up 5/min, reset 3/min (DB-backed)
  • Charge document status transitions enforced as strict state machine
  • Timer concurrency protection via SELECT ... FOR UPDATE
  • CSRF protection via Better Auth nextCookies plugin
  • Charge document re-billing prevention (entries can't be double-billed)
  • Plan limit enforcement uses pg_advisory_xact_lock (TOCTOU-safe)

A05 — Configuration

  • poweredByHeader: false — removes X-Powered-By header
  • productionBrowserSourceMaps: false — no source maps in prod
  • Error responses don't leak stack traces (generic Hebrew messages)
  • .env properly gitignored
  • Sentry inert without DSN configured
  • Contact form has rate limiting + honeypot
  • Cache-Control headers on sensitive endpoints

A06 — Components

  • Zero direct CVEs in project's own code
  • package-lock.json with SHA-512 integrity hashes
  • No lifecycle scripts (postinstall, preinstall) — reduced supply chain attack surface
  • No deprecated packages detected
  • 12 core dependencies clean: drizzle-orm, web-push, resend, react-query, clsx, tailwind-merge, next-intl, lucide-react, dnd-kit, class-variance-authority, @vercel/blob, typescript

A07 — Authentication

  • Brute-force rate limiting: 5 attempts/60s on sign-in (DB-backed)
  • Email verification enforced when configured
  • Password reset tokens expire in 1 hour and are single-use
  • OAuth state parameter and PKCE handled by Better Auth
  • Session ownership validated before return/revoke
  • Sessions invalidated on logout
  • Login returns generic INVALID_EMAIL_OR_PASSWORD (prevents enumeration)
  • Role field has input: false (prevents client-side escalation)
  • Session cache with 5-second TTL and 5-min cookie cache

A08 — Data Integrity

  • No untrusted third-party scripts loaded
  • No external CSS from CDNs
  • Inline script is static (hardcoded theme detection)
  • No eval() or new Function()
  • No insecure deserialization patterns
  • npm ci in CI for deterministic installs
  • Service worker scoped to same-origin, never caches API responses

A09 — Logging

  • Sentry sendDefaultPii: false — no PII sent to Sentry
  • User-facing errors use stable error_code codes (no stack traces)
  • Account deletion logged with logger.info
  • Sentry error capture via logger.error() → Sentry
  • Uncaught errors captured via Sentry.captureRequestError

A10 — SSRF

  • Polar/Resend/web-push SDK clients use server-only configuration

A11 — Framework

  • No secrets in NEXT_PUBLIC_ client bundles
  • Server Components don't expose sensitive data
  • NextResponse usage sets only static headers (no injection)
  • No prototype pollution patterns
  • Proxy correctly gates protected routes

A12 — API & Business Logic

  • Mass assignment prevention: all write endpoints use Zod schemas
  • Pagination on GET /api/entries (capped at 1000)
  • Search result limits (LIMIT 5)
  • Admin role verified on all /api/admin/* routes
  • Timer race conditions prevented via SELECT ... FOR UPDATE
  • Bulk operation limits enforced by Zod (MAX_BULK_ENTRIES = 1000)
  • Charge document state machine enforced in SQL WHERE clauses
  • Input validation on all write endpoints

A13 — Client-Side

  • No sensitive data in sessionStorage
  • Auth tokens managed by Better Auth cookies (HttpOnly, Secure, SameSite)
  • Service worker never caches API/auth data
  • Push notifications properly scoped by user_id
  • Analytics redact PII (UUID segments stripped)
