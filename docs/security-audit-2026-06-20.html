01 Executive Summary

A 13-agent OWASP swarm plus an independent verification pass examined ClockBill's authentication, multi-tenant isolation, billing integrity, payment webhook, client/server state, dependency tree, and CI pipeline. The headline result: no Critical and no High-severity vulnerabilities. The platform's security foundation is genuinely strong — RLS-enforced tenant isolation with no IDOR, parameterized SQL throughout, server-authoritative entitlements that cannot be bypassed, and a signature-verified Polar webhook.

What's working well. Tenant isolation is airtight: every API route checks getUser() and scopes every query by user_id; RLS is FORCE-enabled and bound per request; admin routes require an admin role. No SQL injection (all $1,$2 placeholders; only allow-list/regex-gated interpolation). No hardcoded secrets, no leaked secret values in git history, no NEXT_PUBLIC_ secret exposure. Auth is rate-limited (DB-backed, 3–5/min on credential paths), session cookies are HttpOnly+Secure+SameSite, and logout truly revokes the server-side session. Trial/paywall entitlements are server-resolved and not client-writable — they cannot be extended or reset.
Where to harden. The eight Medium findings are defense-in-depth and integrity gaps, not holes: missing security headers/CSP, a blind SSRF surface in the Web-Push subscription path, a password-reset token reaching server logs on a transient email failure, no rate-limiting on data-export/report endpoints, two charge-document billing-integrity defects, a trivially-fixable transitive dependency HIGH (undici), and no automated dependency/secret scanning in CI. None are exploitable to breach another tenant's data. Recommended sequence: (1) gate the token-log fallback to non-prod, (2) validate the push endpoint, (3) add the security headers, (4) add npm audit + Dependabot to CI and run npm audit fix, (5) fix the two charge-doc billing paths.

Methodology note on rigor: several headline findings from the first-pass agents were downgraded or removed after code-level verification — e.g. "Critical: reset token logged" (actually a dev-only fallback, downgraded to Medium), "fail-open RLS" (actually fail-closed by policy), and "committed secrets" (verified to be .env.template placeholders only). Every Medium+ finding in this report was confirmed by reading the actual code at the cited line — no finding rests on an agent claim alone.

04 Detailed Findings

Click any finding to expand the full context, trigger, and remediation. Locations are real and verified at the cited line.

MediumM-1Missing HTTP security headers (no CSP, frame-ancestors, X-Content-Type-Options)OWASP A05
Location
next.config.mjs:7-21
Agent
A05 — Security Misconfiguration

The Next config defines images, compress, and poweredByHeader:false (good), but has no headers() block. As a result the app ships with no Content-Security-Policy, no X-Frame-Options / frame-ancestors (clickjacking exposure), no X-Content-Type-Options: nosniff, no Referrer-Policy, and no Permissions-Policy. The no-flash theme script at app/[locale]/layout.tsx:135 uses dangerouslySetInnerHTML, which a CSP would otherwise constrain.

Trigger: Any browser visiting the app lacks these protections by default; a CSP-less app is more exploitable if any reflected/stored XSS is ever introduced, and the UI is framable.

Remediation: Add a headers() export in next.config.mjs with at minimum X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, frame-ancestors 'none' (via CSP), and a scoped Permissions-Policy. For CSP, start permissive with report-only, allow the inline theme script via a hash/nonce, then enforce. (Vercel already injects HSTS at its edge for HTTPS domains.)

MediumM-2Blind SSRF via user-controlled Web-Push subscription endpointOWASP A10
Location
app/api/push/subscribe/route.ts:39-55 · lib/push.ts (sendNotification)
Agent
A10 — SSRF

The subscribe handler only checks that endpoint, p256dh, and auth are non-empty, then stores the endpoint verbatim with no scheme/host/private-IP validation. When the daily-reminder or long-timer cron fires, web-push opens a raw https.request() to that stored URL server-side.

Trigger: An authenticated user POSTs an internal/metadata URL as their push endpoint:

// POST /api/push/subscribe
{ "endpoint": "http://169.254.169.254/latest/meta-data/",
  "keys": { "p256dh": "x", "auth": "y" } }
// → server fetches it on the next scheduled push

The response body is discarded (blind SSRF), but the request itself enables internal port-knocking and cloud-metadata probing via timing/status side-channels. Why Medium not High: requires an authenticated account, only fires when a real push is due, and the response isn't returned. Vercel filters the EC2 metadata IP at the platform level, but internal/resolvable hosts may still be reachable.

Remediation: Before storing, validate endpoint: require https:, resolve the host, reject private/reserved ranges (127/8, 10/8, 172.16/12, 192.168/16, 169.254/16, ::1, fc00::/7), and prefer allowlisting the legitimate push providers (fcm.googleapis.com, *.push.apple.com, push.services.mozilla.com, *.notify.windows.com).

MediumM-3Password-reset / verification token URL written to server logs on email send failureOWASP A09
Location
lib/auth/better-auth.ts:278-280 & :303-305
Agent
A09 — Logging & Monitoring

Both sendResetPassword and sendVerificationEmail log the full magic URL when sendEmail() returns false — gated only by if (!sent), not by NODE_ENV. sendEmail returns false both when RESEND_API_KEY is absent (the intended dev fallback) and when Resend is configured but the send fails (transient outage, rate limit, rejected recipient). In that second case — which happens in production — the live single-use token URL is written to Vercel function logs (and reaches Sentry on errors). The URL is the credential until it expires.

Downgrade note: the first-pass agent rated this Critical; verification showed it is a dev fallback that mis-fires on prod email outage, so the realistic severity is Medium. Residual risk is real: anyone with log access during a Resend blip can take over the account.

Remediation: Gate the fallback to non-prod and never log the URL itself:

if (!sent && process.env.NODE_ENV !== "production") {
  logger.info(`Password reset link for ${user.email}: ${url}`);
} else if (!sent) {
  // prod send failure: log only identity, surface a user-facing "try again"
  logger.warn("Reset email send failed", { userId: user.id });
}
MediumM-4No app-level rate limiting on data-export, report-generation, and feedback endpointsOWASP A04 / A12
Location
app/api/account/export/route.ts · app/api/reports/route.ts · app/api/feedback/route.ts
Agent
A04 / A12 — API & Business Logic

Auth credential paths are rate-limited via Better Auth's DB-backed limiter (sign-in/sign-up 5/min, forget-password 3/min at lib/auth/better-auth.ts:325-336 — good). However the heavy server endpoints — full account GDPR export, multi-template report/PDF generation, and feedback submission — have no application-level rate limiting. A single authenticated user (or a scripted free-tier account) can hammer these to burn server CPU / drive up function invocations and egress.

Trigger: Loop GET /api/reports or /api/account/export as fast as possible; each runs multi-query aggregation + PDF/Excel rendering. No backpressure applied.

Remediation: Add @upstash/ratelimit (or an equivalent DB-backed limiter matching the BA approach) keyed by user.id on these endpoints — e.g. 10/min for reports, 5/min for export. This is cost/DoS hygiene, not credential protection.

MediumM-5Charge-document computedLines.amount trusted from the client (not recomputed server-side)OWASP A04
Location
app/api/charge-documents/route.ts:117-131 · schema lib/schemas/charge-documents.ts:11
Agent
A04 — Insecure Design

For fixed_monthly/retainer computed lines, the handler takes amount: c.amount directly from the parsed request body and stores it verbatim into charge_document_lines.amount, summed into charge_documents.total. The Zod schema enforces only min(0) — no upper bound, and crucially no server reconciliation against the authoritative projects.fixed_monthly_fee. This is the classic A04 "trust the client for a computed value".

Impact (honestly bounded): charge documents are the freelancer's own internal settlement record and the basis for the PDF they issue — there is no third party being defrauded, and nothing is auto-filed. The blast radius is the integrity of the user's own document: a client could send amount: 0 to zero a real monthly fee on a printed receipt, or a fabricated large amount. Rated Medium for the principle (server should be authoritative) rather than for external harm.

Remediation: For fixed_monthly/retainer lines, ignore the client amount and re-derive it server-side inside the transaction from projects.fixed_monthly_fee (joined by projectId, scoped by user_id); add a sane max(10_000_000) to the schema and a DB CHECK (amount >= 0).

MediumM-6Charge-document PATCH (add-time-entry) skips billing rounding → inconsistent amountsOWASP A04
Location
app/api/charge-documents/[id]/route.ts:88-99 (compare POST at route.ts:96-111)
Agent
A04 — Insecure Design

When a line is added to a pending document via addTimeEntryId, the SELECT does not fetch p.billing_rounding / c.billing_rounding, and buildLineFromEntry is called with billingRounding unset → falls back to "none". The POST create path, by contrast, selects both columns and runs resolveRounding(...). So the same entry billed via the two paths produces different amounts.

Trigger: Create a charge doc on a quarter_hour_up client, remove a 5-minute line, then re-add it via PATCH — the re-added line bills 5 raw minutes instead of the rounded 15. Silent under-billing / inconsistent receipts.

Remediation: In the PATCH addTimeEntryId branch, select p.billing_rounding AS "projectRounding" and c.billing_rounding AS "clientRounding", read the profile base rounding, and pass billingRounding: resolveRounding(...) into buildLineFromEntry — mirroring the POST path exactly.

MediumM-7High-severity transitive dependency (undici via @vercel/blob) + drifted lockfileOWASP A06
Location
package-lock.json · @vercel/blob → undici@6.26.0
Agent
A06 — Vulnerable Components (live npm audit)

Live npm audit --omit=dev returns 19 advisories: 0 Critical, 1 High, 17 Moderate, 1 Low. The one HIGH is undici <6.27.0 (GHSA-vxpw-j846-p89q WebSocket DoS + 3 lower), pulled transitively via @vercel/blob@2.4.0. Direct exploitability in this app is low (it doesn't use undici's WebSocket client directly), but it trips the "known-vulnerable component" check. Notable moderates: uuid@8.3.2 (via exceljs), nested postcss@8.4.31 (via next), and dev-only esbuild (via drizzle-kit — not in prod bundle).

Second issue: package-lock.json is out of sync with package.json (npm install --package-lock-only produces a 60-line diff) — so npm ci in CI is no longer fully deterministic.

Remediation: (1) Run npm audit fix (non-force — clears undici + babel/otel with zero breaking changes; do not use --force, which would sabotage next/better-auth/exceljs). (2) Add an overrides block forcing { "undici": "^6.27.0", "uuid": "^11.1.1" }. (3) Commit a regenerated, in-sync lockfile.

MediumM-8No dependency / secret scanning in CI (no npm audit, no Dependabot, no gitleaks)OWASP A06 / A08
Location
.github/workflows/ci.yml
Agent
A06 / A08 — CI Integrity

The CI pipeline runs npm ci → lint → tsc → test → build (solid basics, official actions only), but has no dependency-vulnerability gate, no Dependabot config, and no secret-scanning step (gitleaks/trufflehog). Vulnerabilities and leaked secrets are only caught by manual audits like this one — there is no continuous control between audits.

Remediation: Add a CI step after install: npm audit --omit=dev --audit-level=high. Enable Dependabot security updates (free, opens PRs for GHSA fixes). Add a gitleaks pre-commit hook + a gitleaks detect CI step to prevent future secret commits.

app/api/entries/bulk/route.ts:94-106

A04

The bulk PATCH checks destination project ownership but never calls getLockedClientIds, which the single-entry POST/PUT enforce. A free-tier (locked) user can reassign entries onto a locked client's project via bulk. This is a monetization / paywall bypass, not a security boundary — the lock is advisory-on-reads by design — so it's Low. LowL-2No 2FA / passkey; thin password policy (length 8 only)OWASP A07
Location
lib/auth/better-auth.ts:260
Agent
A07

Only minPasswordLength: 8 is set — no complexity, no breached-password check (HIBP k-anon), no max age / reuse prevention, and no 2FA or passkey plugin. Brute-force is impractical (5/min limit), but credential-stuffing from other breaches is the real risk for a billing/invoicing SaaS. LowL-5PII (email) in logs; ~40 routes use raw console.error(error) (stack traces in server logs)OWASP A09

A09

Recipient email is logged on every no-key / failed send. Separately, ~40 API routes bypass the structured logger with raw console.error("…", error), serializing full Error stacks (file paths, driver internals, occasional SQL fragments) into Vercel logs. A04

date is validated only as a non-empty string — a user can log "2099-12-31" or "1990-01-01", shifting revenue across reporting/VAT periods. Remediation: z.coerce.date() with a sane window (≥ today − 2y, ≤ today + 1d), applied to single and bulk paths.

LowL-7Monetary columns lack DB CHECK (≥0) backstop (Zod-only)OWASP A04
Location
src/db/schema.ts (default_rate, retainer_*, fixed_monthly_fee, time_entries.rate, charge_documents.total, charge_document_lines.amount)
Agent
A04

All monetary real columns enforce non-negativity only at the Zod boundary, with no DB CHECK. Any future route/admin path/migration that bypasses Zod could write a negative rate → poison billing. The DB is the last boundary (Iron Law 5). Remediation: add CHECK (col IS NULL OR col >= 0) on these columns. Note the VAT snapshot column is CHECK'd to 0–100 — good model to follow.

A03
